## Camera state model

`resolveCameraState()`/`resolveAllCameraStates()` (`src/luna/runtime/lunaCameraResolver.ts`) — the single authoritative resolver, mirroring `resolveBuildingPower()`/`resolveFireState()`/`resolveHvacState()`/`resolveAccessAuthorization()`. States limited to ONLINE/OFFLINE — the only states the runtime's own `online` field and the pre-existing `camera-offline` scenario actually support. FAULT/MAINTENANCE were deliberately not implemented.

## Camera capabilities

Zero, for all four cameras — no LIVE_VIEW, PTZ, ZOOM, SNAPSHOT, RECORDING, PLAYBACK, or EVENT_SEARCH was fabricated. The Control Board's command area correctly renders nothing; the asset panel explicitly discloses why.

## Physical geometry

`CctvPlantEquipment.tsx`'s `CameraGeometry` — a recognizable bullet-camera body/bracket/lens with a real-state LED, manufacturer-neutral REFERENCE DESIGN, replacing the generic marker box. No field-of-view cone was added, since the brief's own instruction that such a cone must never determine authorization/event truth made omitting a purely decorative element the more honest choice for V1.

## Controls

Seventh `SystemControlBoard` consumer (`CctvControlBoard.tsx`), four real tabs (Camera 01 default/02/03/04), a live `CctvStatusSummary` header widget, and an `AccessCorrelationSummary` section shown wherever a real `monitored_by` relationship exists. The apartment intercom is deliberately not a board tab (HIDDEN to Facility).

## Access event correlation — the central feature

Two real, canonical `monitored_by` edges added to the pre-existing relationship array (no new relationship type needed): Main Entrance↔Ground Entrance Camera, and the apartment lock↔video intercom. Every other access-point/camera pair was deliberately left unresolved rather than guessed from proximity. Verified end-to-end: a real GRANTED/DENIED event at the governed lock is immediately reflected in the intercom's own narrative and correlation summary; a camera going offline never writes to the Access event log (Access remains the sole event owner/producer).

## Oyi

All 8 of the brief's own target phrases verified end-to-end. `matchCctvInvestigation` resolves aggregate/investigation questions deterministically (never reading live state inside the parser itself, matching every other matcher's purity). Every new vocabulary pattern was checked for substring collisions against the full existing pattern list and every other system's own target phrases — Electrical/HVAC/Access/Water phrases all re-verified unaffected.

## Permissions — no defect found, no change made

Common cameras: `FULL_3D` for Facility, `HIDDEN` for any resident (unchanged pre-existing rule — a resident does not gain Facility CCTV visibility merely because a camera exists in common space). The private apartment intercom: `HIDDEN` to Facility, `FULL_3D` for the assigned resident (same pre-existing private-unit rule as the entrance lock). Proven via a full Oyi controller round-trip: the assigned resident's investigation of "the camera associated with the last denied access" succeeds completely; the identical Facility request is denied completely. The camera never becomes an authorization authority, and private-unit privacy holds even for security investigation. `lunaRepresentationPolicy.ts` was not modified.
